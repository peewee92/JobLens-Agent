# 批量匹配：单轮五个岗位

## 需求卡

- 用户：导入岗位或更新资料后，需要处理一批已准备岗位的人。
- 原问题：旧批量匹配每轮上限为 10，与主业务方案的 5 不一致；旧导入入口仍提示可能自动调用模型。
- 目标：一次请求最多选择 50 个岗位、最多处理 5 个已准备岗位；其余岗位返回 `resumeJobIds`，用户自行决定是否继续。两个网页入口展示同样上限与零预算边界，部分失败仍明确告知。
- 不做：不自动继续、不改变已有结果、不保证旧入口复用已有匹配报告、不调用真实模型。
- 契约：`packages/contracts/schemas/match-batch-execution-request.schema.json`；服务端字段默认值和上限与共享契约一致。旧客户端请求超过 5 将收到 422，需更新客户端。
- 验证：真实 HTTP 与应用服务组合的 50 岗离线替身测试，首轮处理 5 个、显式第二轮再处理 5 个；另有服务端边界、50 岗十轮、失败隔离和契约一致性测试。网页测试与类型检查通过；真实浏览器多轮操作尚待验证。

## 决策与失败例证

限制在服务端和网页同时执行，不能只在按钮文案限制；所有被截断的岗位保留在继续集合中。失败例证：旧客户端提交 `maxReadyJobs=6`，新接口应返回 422 而非默默扩大执行范围。面试表达：调用方选择上限不能覆盖服务端资源边界，下一批必须由用户主动发起；需要模型但无授权的岗位仍保持明确失败，不伪报整个批次成功。

## 多轮界面验证及修复

- 使用仓库组件副本及隔离的模拟接口在浏览器实际操作 8 个岗位：首轮 5 个中 4 个成功、1 个因授权受阻，余下 3 个只在再次点击后执行。
- 发现旧组件在第二轮成功后隐藏第一轮失败并自动跳转。现两个批量入口都累计当前页面会话的失败数量和授权提示；有失败时导入入口不自动跳走，用户能看到尚有岗位未完成。
- 再次浏览器操作确认：首轮显示“累计 1 个未完成”，显式继续后仍显示该失败。此验证使用模拟接口，未证明真实数据库端到端执行；跨页面刷新后，这些旧批量入口的页面内累计状态不持久化，应以岗位与匹配记录重新核对，不应把它当作持久运行记录。

## 未完成岗位的下一步

- 批量入口现在列出当前页面会话中未完成的岗位及直达链接，分别说明授权、输入、存储和一般失败；已推迟到下一轮的岗位不误列为失败。
- 有失败时暂不自动刷新服务端页面，避免父页面按新数据移除组件而丢失错误与链接。成功结果已由服务端保存；用户可通过岗位详情核对，刷新后当前会话列表不保留。
- 自动测试覆盖跨轮保留、延后项排除、按岗位更新和成功后移除；网页 237 项及类型检查通过。浏览器用隔离模拟接口验证第一轮授权受阻的岗位链接在第二轮成功后仍显示，未验证真实数据库异常或刷新恢复。
