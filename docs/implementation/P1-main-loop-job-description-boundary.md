# 岗位要求分析：描述长度边界

## 需求卡

- 用户：导入岗位后，需要知道岗位描述是否能够进入要求分析，以及不能分析时该怎么处理。
- 原问题：后端要求去除首尾空白后的描述为 40 至 50000 个字符；前端只检查最短长度，还按 UTF-16 单元计数。过长内容或 39 个表情符号可让用户进入实际必然失败的分析；旧要求需要重新分析但新描述无效时，阻断提示仍要求点击禁用按钮。
- 目标：岗位详情及导入页根据描述长度展示短、过长或可分析状态；短描述提示重新采集完整职责和要求，过长提示检查采集内容。没有读取到岗位详情时，不把未知描述判定为过短。
- 不做：不截断或改写岗位事实，不改后端校验、数据或接口，不发起分析或模型调用。当前采集途径是否能修复每一种来源的描述仍需实际来源验证。
- 契约：后端工作流的 40—50000 字符限制仍为权威，前端字符计数按 Unicode 码点近似后端；边界条件由双端测试固定。首尾特殊空白的语言运行时定义可能不同，后端校验仍是最终保障。

## 验证与面试口述

- 技术决策：输入无效时尽早告知用户，但服务端仍是最终裁决，不能为了通过界面校验而截断岗位原文。
- 可复现失败：39 个表情符号在旧前端占 78 个 UTF-16 单元、超过 40，却被 Python 按 39 个码点拒绝；50001 个中文字符旧前端也会放行但后端拒绝。
- 本轮验证：前端类型检查、284 项测试通过；真实 SQLite 的后端工作流边界测试 5 项通过。合成数据库副本构造超长描述，浏览器导入页显示“岗位描述过长”，岗位详情的分析按钮禁用并显示修复提示。此验证不包括重新采集真实来源、实际模型提取或数据库迁移。
- 面试口述：我分别验证界面提示和服务端执行边界，区分用户体验与权威校验；测试覆盖 Unicode 长度差异和上下限，而不是假设浏览器的字符串长度与 Python 相同。
