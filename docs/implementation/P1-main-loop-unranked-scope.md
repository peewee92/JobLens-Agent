# 分析范围：未进入排序的岗位必须可见

## 需求卡

- 原问题：用户选择多个岗位时，排序工具只返回有可用报告且符合默认排序规则的岗位；部分岗位无结果时流程仍可继续，但确认页面及保存结果未说明遗漏范围。
- 本次行为：从持久运行的原始请求与实际排序岗位计算差集；目标确认、结束状态和重开的保存结果展示每个未进入排序的岗位，并提供岗位详情链接。提示明确区分“未排序”与“能力不足”，不猜测具体原因。
- 契约：`unrankedJobIds` 为结果接口的可选新增字段，由该运行已保存的请求和排序状态计算；原有保存材料不重算、不修改。共享 JSON Schema 已更新。
- 不做：不为了填满推荐而编造结果；不自动生成缺失匹配报告、不调用模型。此切片在排序后提示范围，开始前逐岗位预检仍需补齐。
- 技术决策：保留对部分有效岗位的人工确认能力，同时明确未排序岗位，而不是将其静默归为不适合或把全部运行阻断；结果重开从服务端运行状态重建差集，不依赖浏览器缓存。
- 复现：两岗位中一个没有可用报告时，旧流程只显示一个排序结果，未解释另一个；现在确认前可见、确认后和历史结果仍可见。
- 面试表达：排序返回集合不等于用户请求集合；我们把两者的差集作为事实范围告知用户，不以缺失结果推断资格。

## 验证

- 真实 HTTP、SQLite 和运行处理器测试：选中一个有报告岗位及一个无报告岗位，确认目标、保存结果、重开两次，均保留未排序岗位；共享契约与生成接口一致。后端相关 20 项测试通过。
- 页面 240 项测试和类型检查通过，生产构建通过；浏览器在隔离合成数据库实际完成部分排序、确认和打开结果，三个界面均能看到未排序岗位。最后补充的部分范围计划文案另通过类型检查和网页测试。
- 限制：原因是类别提示而非逐岗位精确诊断，历史结果详情对非目标岗位显示标识而非当时标题；浏览器测试未覆盖所有 blocked 或陈旧数据原因。
