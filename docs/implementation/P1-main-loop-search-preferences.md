# 阶段 2B：求职偏好参与确定性判断

## 需求卡

- 用户：已确认资料与求职意向、正在选择真实岗位的求职者。
- 原行为：排序仅粗略使用软偏好；城市、薪资、远程与自由文本限制未进入资格判断。
- 本轮切片：城市、最低月薪、远程和排除关键词参与同一资格入口；角色名称只能直接支持、不能据不一致淘汰；级别、工作形式及自由文本硬条件没有可靠结构化岗位字段时明确待确认。
- 不做：不解释任意自然语言硬约束、不重建岗位事实库、不调用模型，不实现完整工作台或运行持久化改造。
- 契约负责人：应用层负责规则；共享契约负责偏好检查形状；网页消费后端结果，不再自行判断。
- OpenSpec 当前未安装／初始化，使用此需求卡。

## 规则与验收

1. 城市采用明确城市标记比较；接受远程时“目标城市或已确认远程”均可，不要求必须远程。异地且远程未知为待核实；异地且明确不远程为冲突。
2. 不接受远程且岗位标为远程为冲突，未知则待核实；未设置不施加独立远程约束。
3. 岗位薪资上限低于底线为冲突；下限达到底线为支持；区间跨底线、缺失或异常均待核实。只比较现有统一 K/月字段，不推算奖金或年包。
4. 排除词仅检查岗位名称和公司，英文按词边界；不把原始 JD 引入 Match/Gap/Prepare。
5. 自由文本硬条件保留原文并待确认，不静默忽略或自行解析。目标级别和工作形式同样明确提示当前不能比较。
6. 偏好冲突优先于语义模型结果；报告保留偏好检查及意向身份版本。规则升级为 v3，不重写 v1/v2。
7. 当前排序只使用意向版本和偏好输入指纹仍一致的 v3 报告；意向或岗位关键字段变化后要求重新分析，而非临时改写旧报告。
8. 网页逐项展示原因与事实字段引用；服务端检查意向在预检后变化时拒绝运行。
9. 验证纯规则、实际用例、SQLite 快照、过期排序、接口与浏览器；新建隔离副本，零收费调用。

## 分拆后的下一步

2C 处理推荐分组与跨页面历史提示；阶段 3 处理整个运行的原子迁移和最终提交版本复核。本轮前置检查不等同于消除并发修改竞态。

## 技术决策、失败与面试解释

- 决策：偏好检查与岗位能力要求分开存放，不伪造 JobRequirement ID；统一合成资格结论，复用原有匹配与报告流程。
- 失败复现：武汉＋接受远程的用户遇到武汉线下岗位，不应因不是远程而被淘汰；薪资 15–25K 遇到 20K 底线不能说已满足，也不能说确定不满足。
- 面试口述：“我把用户偏好作为有版本的事实来源接入原有流程。能确定比较的规则直接执行，不能比较的明确待确认。报告保存当次判断，不随用户修改偏好而变化；新排序只接纳当前输入版本，避免历史结论被悄悄重解释。”

## 本轮结果

### 已实现

- `app/application/search_preferences.py`：纯规则，不读取原始 JD、数据库或模型。资格用例同时核对意向身份版本，合成总判断。
- `PreferenceCheck` 沿既有资格 → 语义匹配 → 报告路径传递；偏好冲突时复用现有短路路径，跳过语义匹配。偏好检查与岗位要求计数明确分开。
- SQLAlchemy JSON 快照追加规则 v3、意向身份版本、检查与内部指纹，不新增数据库迁移。旧 v1/v2 保留历史，不进入当前排序。
- 岗位页、报告卡与推荐卡共用偏好依据组件；明确冲突默认展开，提供直达求职偏好表单的修复入口。没有岗位要求风险不再被描述为没有任何风险。
- MCP 核心协议和业务实现未重做；仅更新纯合成演示库，使其报告绑定当前意向和事实，避免新规则下旧演示快照失效。STDIO 重启与工具调用回归通过。

### 本轮验证

- 后端全量 **1472 项通过**；覆盖资格、偏好规则、身份变更、匹配与报告传递、真实 SQLite 快照、排序过期、API 和 MCP 协议。
- 网页 **176 项通过**，新增共享样例的实际组件渲染测试，不只检查源码字符串。类型检查、生产构建与 `git diff --check` 通过；收尾定向回归 **101 项通过**。
- 只读真实数据核对 **20 个岗位**：仅就当前偏好检查而言，5 个有支持、15 个角色范围待核实，0 个明确冲突。**不代表 5 个岗位已完整匹配成功或值得推荐**。无模型调用或业务写入，源副本哈希不变。
- 浏览器使用独立纯合成数据库：武汉线下岗位＋接受远程仍得到地点支持；自由文本“不接受长期驻场”明确待确认。把底线改为 40K 后，岗位上限 30K 出现明确薪资冲突。
- 浏览器点击生成完整建议：保存一份 v3 报告，`providerCalls=0`、`dbWrites=1`（仅合成库）；实际响应通过共享 JSON Schema 校验。默认排序 0 条，显式包含阻断项时 1 条。
- 通过实际意向 API 更新到下一版本后，旧报告从当前排序消失；直接检查数据库，原历史快照完全不变。
- 修复入口确实打开求职偏好表单。截图与运行证据仅放在临时目录 `/tmp/joblens-preferences.ffFkbn/`，无真实职业资料进入截图。
- 首轮回归暴露旧 MCP 合成报告未绑定意向、因而不再可排序；已修正演示数据并重新通过协议测试，没有放松生产排序规则。
- 组件渲染首轮发现独立测试进程缺少 JSX 的 React 绑定；补充显式导入后通过。未为此安装新工具或依赖。

### 边界与后续

- 城市只支持保守的规范标记；不做地理编码或任意地址／多地安排推理。
- 自由文本限制、级别、工作形式只呈现待确认，目前没有逐条人工确认写回岗位事实的入口；不能宣称已经满足或自动执行这些限制。
- 修改任一意向版本会使当前报告过期；复用不变的语义匹配产物以降低重算成本，留给后续运行收敛阶段。
- 当前排序为空时，仅依赖既有覆盖检查与分析入口；统一“为什么过期”的用户提示属于 2C。
- 工作区旧材料、完整报告刷新重开和最终保存前原子版本复核仍未完成；不能把本轮预检、指纹过滤说成完整并发保护或持久化恢复。
