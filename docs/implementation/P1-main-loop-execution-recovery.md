# 阶段 3B-2：执行领取与显式继续

## 需求卡
- 用户：分析期间刷新、服务重启或重复提交的单用户。
- 原行为：状态条件更新防止覆盖，但业务计算前没有领取；排序首个保存前无运行记录，重启后不能明确继续。
- 目标：正式主数据库先保存 created，再以短事务领取运行；计算在事务外；每次状态提交校验有效租约令牌。过期后可以重新领取，旧执行者不能保存或释放新租约。
- 恢复：GET 不执行；POST continue 只推进 created、已保存排序或已确认分析；等待确认和终态不推进。恢复只读计算允许重算，不承诺恰好一次。
- 边界：本切片无模型调用，无后台调度、自动续租或付费重试；租约超时后停止后续步骤，用户显式继续。
- 契约：应用服务负责继续规则；主运行仓库负责原子领取与提交围栏；共享接口增加继续请求。
- 验收：真实 SQLite 两执行者只有一人领取；过期旧执行者保存及释放失败；created、排序后及分析前故障重开继续；GET 无事件增长；迁移只验证数据库副本。
- 旧测试适配器维持冻结调用语义，不作为正式租约能力证据；正式依赖必须使用主运行仓库。
- 不提交、不推送、不修改真实求职数据库、不调用收费模型。OpenSpec 未初始化，采用轻量需求卡。

## 技术决策与边界

复用已有执行租约的条件更新思想，租约直接挂在主运行行，不另造分布式锁服务。随机令牌只在有效租约期间授予提交权，释放也必须匹配原令牌；数据库事务不跨越工作流计算。开始先提交 created，使排序之前的异常也有可找回的输入；保留数量限制和命令摘要。

运行租约不等于外部调用恰好一次。本轮覆盖的是零模型、只读工作流；没有后台自动继续或续租，默认 120 秒到期后由用户继续。仍需后续步骤级尝试记录、模型授权与结果不确定计量，不能据此宣称全部运行治理已交付。

## 可复现失败与修复

在隔离数据库给完成事件插入添加故障触发器。确认决定及事实校验已经保存，但完成事务回滚；刷新只读取 skill_gap_ready，不自动重新计算。移除故障后点击继续，最终状态与事件一同提交，原 actionId 保持不变。

浏览器故障回放还暴露出旧仓库把所有 IntegrityError 当成唯一键竞争。已将非唯一约束保存错误分类为 503 career_agent_save_failed；唯一键或修订竞争仍为 409。错误提示不泄露数据库原始异常。运行中也不再同时展示“已结束”和新建按钮，避免误导用户放弃可继续分析；只有指纹时明确说明完整快照未保存。

## 面试口述

我把恢复拆成三个问题：有没有保存已接受输入、谁现在有权执行、结果是否与状态一起提交。先持久化输入，再用短租约领取；工作流在事务外执行，保存时既检查修订也检查有效令牌。旧进程即使晚返回也不能覆盖新进程。刷新只读，用户显式继续；只读计算允许重算，不虚构外部调用恰好一次。

- 最终后端全量 **1528 项通过**，网页 **185 项通过**，TypeScript 与生产构建通过。第一轮网页发现一项旧文案断言，已更新为不冒充原始快照的准确文案后通过。
- 真实 SQLite 并发领取、过期令牌、禁止无租约覆盖、旧执行者释放保护、输入保存后故障、排序后故障、已接受决定后故障和 GET 不执行均有集成测试。
- 合成副本和已有真实数据的新副本升级 0023→0024：36 张原有表的数据校验、完整性、外键、就绪检查通过；真实数据库和源副本未改。
- 浏览器使用 Chrome 在隔离合成数据上完成：低证据阻断及刷新保留原因；两个目标进入人工确认；注入完成保存失败后刷新看到显式继续；移除故障后点击继续完成。实际停止并重启服务后再次读到相同完成结果。
- 最新代码实际 HTTP 复验：保存故障返回 503，已确认状态仍为 resuming/skill_gap_ready，显式继续完成为 revision=5。仅接受一个人工决定，六次追加迁移（0–5）；浏览器路径前后职业业务表内容一致，模型调用为零。
