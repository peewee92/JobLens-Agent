# 阶段 3B-1：重复命令内容一致性

## 需求卡
- 用户：网络重试、刷新或多标签页操作的本地求职用户。
- 原行为：开始只比较运行及请求标识；确认只比较 actionId；复用标识但更改岗位、数量或决定，会静默返回另一请求的结果。
- 目标：同标识且同规范化内容重放不增加事件；不同内容明确冲突。摘要与被接受的状态同事务保存，不增加第二套状态表。
- 契约归属：运行应用服务及人工确认边界；摘要为内部持久字段，不暴露职业资料，不改变 MCP 形状。
- 规范化：保留岗位顺序，去重；数量、决定、等待点及显式所选岗位均纳入版本化摘要。忽略字段也不能悄悄改变已接受请求。
- 旧数据：没有摘要的已接受命令不能证明内容一致，拒绝重放并提示新分析；只读查询仍保留。
- 不做项：不声称执行租约、显式继续、完整结果快照已交付。
- 验收：真实 SQLite 同内容重放不新增事件；不同范围、数量、决定、等待点或目标冲突；重新实例化服务后语义不变；摘要不可被后续迁移改写。
- OpenSpec 尚未初始化，使用轻量需求卡；不调用付费模型、不修改真实数据库、不提交或推送。

## 技术决策

在运行内保存带版本的规范化 SHA-256 摘要。开始内容随首个状态保存；人工决定的摘要随决定迁移提交，复用已有事务，不增加通用命令平台。字段没有出现在公开运行响应中；没有记录简历、岗位全文或密钥。

摘要约束已接受命令的内容，不代表取得了执行租约。两个同时到达、尚未保存首个状态的请求仍可能重复只读计算并产生一次修订竞争；后续 3B-2 处理执行领取，不承诺此时所有并发同内容请求均直接得到成功响应。

## 可复现失败

先用某个 requestId 分析岗位一、二并取前一名，再复用全部标识改成取前两名。旧实现直接返回前一次结果，掩盖请求差异；新实现返回明确的 409，不改写原结果。人工确认后复用 actionId 更改为拒绝、修改等待点或选择其他岗位，同样拒绝。

## 面试口述

幂等不只是看标识是否相同，还要证明业务内容相同。我先规范化岗位列表和数量，保存请求摘要，再把人工决定与摘要同事务提交。重试可以得到已接受状态，但不能借同一个标识偷偷更改决定。摘要解决语义一致性，租约解决谁能执行，两者不能混为一谈。

## 后续不缩减

3B-2 接入短租约及过期执行者保护、显式继续、服务端最近运行和网页发送前保存命令。3C 固定事实版本并保存完整结果；之后继续工作台、工作区、反馈与限定范围重分析。当前仍不宣称全业务闭环完成。
