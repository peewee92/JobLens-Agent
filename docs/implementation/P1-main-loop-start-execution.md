# 主业务闭环 4A：从保存的分析开始执行

## 需求卡（2026-10-25）

- 用户：已经确认目标并有完整分析结果，需要一次操作进入可跟踪的准备工作。
- 原行为：分析结果只能查看；用户要逐个建立工作区、保存简历事实和行动，工作区还会读取最新资料生成材料。
- 目标：结果页点击“开始执行”，在一个数据库工作单元内创建/复用所选目标的工作区，关联不可变分析材料，保存有证据的简历事实草稿并建立行动。返回可打开的工作区。相同请求重试和不同标签页不重复创建；事实过期禁止首次建立新材料，但允许查看与记录人工状态。
- 拆分：4A 本轮接通结果到工作区；4B 首页工作台只读汇总和明确下一步；阶段 5 反馈、事实确认、更新分析。
- 不做：模型调用、自动投递、额外 Agent、后台任务、原生 LangGraph 中断迁移。
- 架构：应用服务组合既有工作流；调用方 Session 管理事务。准备材料引用原分析，不复制成另一套算法或重新读取最新资料。保留工作区创建时来源，当前分析引用独立更新。
- 命令契约：POST `/career-agent/runs/{thread_id}/execution`，`commandId/resultId/jobIds`（1～5 个原确认目标）。同标识同内容返回原结果，同标识不同内容冲突；GET 查询已关联工作区无副作用。
- 回滚边界：整个岗位范围的工作区/简历草稿/行动/时间线/命令回执一起成功或回滚。提交结果未知时复用网页发出前保存的原命令，不生成新标识。
- 验收：真实 SQLite 原子回滚、并发、同/异内容重放、事实过期、历史材料读取；网页实际点击开始执行、打开工作区、改变行动状态并刷新；迁移仅验证新副本。
- OpenSpec 未安装且未初始化，使用本需求卡。保留已有未提交工作；不提交、不推送、不修改真实求职数据库。

## 完成标准

用户从已保存分析无需命令行即可到达带有准备材料和可操作行动的工作区；没有证据时不制造简历内容；没有学习缺口时仍可围绕真实岗位要求安排简历核对与面试准备，不能伪造技能差距来凑行动。

## 本轮实现与验证

- 应用服务 `StartAnalysisExecutionUseCase` 复用既有工作区、简历事实与行动工作流；相同准备材料使用内容摘要复用，重复分析不重置人工行动/投递状态。工作区保留初始来源，独立关联当前分析；每项行动保留创建时分析引用。
- 主库迁移 `20261025_0026`：工作区/行动来源引用、命令回执。SQLite 短写事务串行化领取、事实检查、所有业务写入与回执；同标识不同内容冲突。同结果不同命令可复用，无新增运行状态机。
- GET 工作区材料、简历事实与面试问题读取原始保存分析；资料变化后仍可查看，禁止据旧事实新建材料，不阻止人工记录结果。未完成反馈回流的跨步骤事务改造，不能声称所有旧写接口已原子化。
- 网页发出前保存原命令；刷新保留待核实请求，查询不产生副作用。默认展示最重要的 3 项行动及其要求来源、目的和完成标准。简历/面试准备完成只记进度，不会自动生成技能证据。

### 决策、失败例证与面试口述

- 决策：将“开始执行”作为保存分析之后的独立业务命令，不延长 Agent 等待周期；准备材料引用原分析，工作区管理长期人工进度。事务外没有模型调用，因此整个命令可以用一个短 SQLite 事务保障全有或全无。
- 可复现失败：在隔离库给 `analysis_execution_receipts` 加 `BEFORE INSERT ... RAISE(ABORT, ...)` 触发器，再发开始执行请求，预期 503 且五类业务表无部分写入；移除触发器后重放同一命令成功。见 `test_analysis_start_execution.py`。
- 面试口述：我没有增加第二个 Agent，而是把已有分析产物接到长期工作区。请求重试靠持久化命令摘要，业务写入靠单库事务，历史解释靠不可变分析引用。学习和准备进度不会直接变成职业事实；新增事实仍必须经过用户确认。
