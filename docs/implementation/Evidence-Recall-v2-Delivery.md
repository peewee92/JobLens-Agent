# 真实岗位证据召回修复（2026-11-02）

## 需求卡与边界
- 用户问题：已确认经历包含技术和职责线索，长中文岗位要求却全部未召回；界面三个 0 掩盖了尚未判断的要求。
- 完成标准：有明确线索才召回，每条最多 3 条；候选不等于满足；显式授权才语义判断；五类统计覆盖全部要求；历史保持原样且旧版本不能进入当前排序。
- 不做：向量库、新检索模型、修改职业事实、自动付费重试、重写排序或准备工作流。
- 契约：`packages/contracts/schemas/match-report.schema.json`，Python 和 TypeScript 同步消费。

## 已实现
1. `evidence-retrieval-v2`：明确技术词、可审查的职责同义组、词边界、去重和稳定顺序；精确关联优先，职责线索只为相关候选。保留原有“仅相关候选不能被模型提升为完全匹配”的校验。
2. 授权摘要包含召回版本与完整候选内容；事实或规则变化使旧授权失效。无候选不调用模型。候选摘要不静默截断。
3. 仍保留一次请求、60 秒最大超时、4096 最大输出及 12,000 字符输入上限。大小检查改为工作流和模型适配器共用的实际业务输入序列化，不再重复计算内部资格和审计记录；超限明确阻断，不拆分付费。
4. 报告增加可缺省的 `retrievalVersion`；每条增加 `candidateCount` 与 `assessmentSource`。历史缺失值为未知，不假定零候选，不需要数据库迁移。
5. 五类互斥统计：已有支持、部分支持、证据未覆盖、待核实、明确硬冲突；无候选的新报告显示未进行语义判断。历史对照同时检查召回版本，避免把规则变化当作能力变化。
6. 旧报告、已保存分析及工作区不被改写。显式重新匹配复用仍有效的岗位要求，不要求重新提取。

## 用户复测步骤
更新代码对应的本地服务后，打开原岗位，点击“重新生成完整匹配建议”，核对要求和候选摘要，再按需单独授权一次语义匹配。不需要再次付费提取仍有效的岗位要求。刷新可重开报告；旧报告保留且显示检索规则已更新。之后返回岗位比较并重新检查。

## 设计取舍与面试口述
失败例证：完整英文能力标签与中文职责句不相等，原检索得到 0 个候选；这只能证明检索没有找到线索，不能证明用户没有能力。

采用小型受控词表而非向量检索，是为了在当前单用户场景保证成本、可解释性和可回归验证。职责同义只打开比较机会，模型输出仍受证据引用及相关候选上限约束。把检索版本和候选内容绑定到授权，避免用户同意的是一组经历、实际判断的却是另一组。

后续限制：差距与准备工作流仍以已确认技能关联为主要依据，部分语义支持不会自动变成已确认技能或职业事实；本轮没有重写该业务口径。真实模型质量和独立用户试用需分开验收。
