# 主业务闭环 2C：保存的匹配结果

## 需求卡（2026-10-25）

- 用户：完成过匹配分析、希望刷新后继续查看的本地用户。
- 原行为：结果已持久化，但页面只保存在组件内存；过期报告从排序消失，没有结果页解释。
- 目标：只读查询和重新打开原始结果；显示事实、意向、要求与策略版本变化，不静默重算历史结论。
- 本切片：历史列表、指定结果打开、当前性共用规则、稳定排序；四组推荐展示作为随后独立切片。
- 不做：新增模型调用、运行存储迁移、工作台重建、历史数据改写。
- 契约：后端应用层拥有当前性判定；共享契约拥有历史接口结构；网页只展示原因。
- 失败：历史读取失败明确提示；不存在的指定结果不回退冒充；缺少当前资料不妨碍读取历史。
- 验收：真实 SQLite 读历史无写入；当前、过期、旧策略、错误岗位与刷新重开；相关回归及浏览器验证。
- OpenSpec：当前未安装、未初始化，使用本需求卡，不安装工具。

## 技术决策

历史是不可变的原报告，当前性是只读派生信息，两者分开；排序复用相同判断。GET 不生成分析、不调用模型。

## 可复现失败

旧实现：生成匹配结果后刷新岗位详情，组件 report 恢复为 null。数据库仍有结果，但用户看不到。修复后服务端读取持久化历史。

## 面试口述

我把“历史上分析了什么”和“今天是否仍可用于排序”分开：历史报告保持原样，当前性由资料、偏好、要求和策略版本决定。这样资料变化不会污染历史解释，用户也能知道结果为什么过期，而不是看到报告突然消失。

## 后续顺序

2C 推荐四组及目标建议边界 → 3 单一运行存储与恢复 → 4 工作台及工作区一键创建 → 5 事务与事实反馈更新 → 6 三条离线路径与授权真实验收。每项分别验证，不把本切片当成全闭环完成。


## 本轮验证结果

- 后端全量：1482 项通过；新增真实 SQLite 历史／原样保留／只读 SQL 与 HTTP 测试。
- 网页：179 项通过；TypeScript 检查和生产构建通过。
- 共享契约：实际 HTTP 历史响应通过 JSON Schema 校验，包含旧演示快照的零写入历史计数。
- 浏览器：指定历史链接 → 刷新保留原结论；旧策略和意向变化显示原因；错误结果标识不回退；当前结果显示版本。
- 浏览器重新生成：隔离合成 SQLite 中通过薪资硬冲突确定性路径生成新报告，`providerCalls=0`，历史从 4 份追加到 5 份，刷新后仍有当前保存结果。
- 证据：`/tmp/joblens-history.1QEtCc/`，含测试日志、合成数据库、HTTP 响应、`history-reopen.png` 和 `history-after-regenerate.png`。临时证据不提交。
