# P1 · 首次分析失败恢复与岗位比较范围

## 需求卡

**用户与任务。** 第一次打开 JobLens，带一份简历和几条岗位描述，想确认哪些值得优先准备、哪些暂时不能下结论。

**观察。** 冷启动试用里，硬件岗位的离线要求分析明确失败却提示「可能已保存，请刷新」；选择三条岗位，比较前只识别出一条可排序，但按钮仍承诺比较三条。无法分析的岗位统一写「尚无匹配报告」，回到岗位也不知道下一步。

| 步骤 | 新行为 | 可观察验收 |
| --- | --- | --- |
| 空库进入比较 | 展示职业资料与添加岗位入口，不呈现无效的选择区 | 无岗位时，两条链接可用；已有岗位但没有职业资料时仍不能生成匹配 |
| 分析单个岗位要求 | 离线分析遇到明确拒绝，就地说明本次没有保存结果，提示检查原文、主动重试或跳过。网络中断或不明响应先刷新核对 | 结构化 502/503 与不明网关响应表现不同；等待期间和结果未确认时禁止重复提交；重试要再次确认 |
| 核对硬件岗位 | 离线样本能识别原文中的「数字电路测试」，不放宽分析门槛，也不绕过人工核对 | 原文仍可核查；5 年门槛与已确认的 2 年经历冲突，得到明确的不满足结论 |
| 检查与比较 | 对未参与岗位解释是缺原文、分析未成功、要求待确认、缺报告、报告过期、还是硬性条件冲突。显示当前可比较数量；正式结果显示原选择数和实际比较数 | 返回岗位修复时保留原选择，须重新检查；零条可比较不能启动；不自动改写正式请求中的选择范围 |

三步引导重排、批量粘贴、手工补写岗位正文、简历确认流程、所有页面的术语与异步反馈统一，留到下一轮。匹配结论不是录取概率；遗漏不等于没有能力。真实模型授权、岗位要求确认、目标确认和历史材料均按原规则处理。无数据库迁移、无在线模型调用、无自动投递。

## 技术决策

- 冷启动复测发现，手工表单在网页脚本接手前可能退回原生 GET 提交。等待这一小段时间时禁用保存按钮，且设为 POST 防止将岗位正文带入地址。

- 判断「确定失败」时同时校验状态码和已知错误分类；其他不明响应不能推断没有写入，保留刷新优先。
- 排序前检查的 `omissions[].recoveryCode` 是可空的说明字段，由服务端根据当前岗位与报告计算；前端可兼容旧响应或未来分类。根据岗位 ID 和去除首尾空白后的当前描述哈希，只在最近一次尝试明确是离线失败时给出该分类，且不公开内部错误或追踪内容。它不改变正式排序策略，也不写入历史快照。
- 离线样本的新能力别名按原文精确匹配，产物标记为 `fixture-requirement-extractor-v2`，历史版本不改。匹配继续基于已确认的岗位要求与用户真实经历。

## 可复现失败

在离线样本模式添加一条足够长的描述：「任职要求：熟练掌握光刻机校准，能独立完成板级调试和信号完整性验证。」加上一条明确 5 年的从业要求。样本不认识该技能，分析会明确拒绝并且不保存岗位要求。页面应给出核对原文和显式重试的入口；返回比较前检查，应标为「上次分析没有保存岗位要求」，不是「描述太短」或「当前不匹配」。

## 验证方式

- 后端：`test_first_run_recovery.py`、`test_ranking_preflight.py`、首次及三岗位闭环测试。核对硬门槛、排除原因、同版本分析记录，以及查询无写入、无调用。
- 前端：`requirement-extraction-outcome.test.ts`、`agent-ranking-preflight.test.ts`，另做类型检查。
- 浏览器：新 Chrome 会话和新数据库，上传同一份合成 PDF，录入三条原岗位和额外错误样本；核对错误反馈、比较前检查、部分结果、准备材料和行动刷新恢复。

**面试口述。** 我先从空库模拟了一个没有操作说明的求职者，发现真正的阻断是失败反馈不可信和比较范围不清。修复后，一条硬件岗能明确说明年限冲突；信息不完整的岗位仍不会收到编造的结论。预检只读，正式分析保留原范围并重查事实；用同一份合成素材和故障样本重跑验证，不把测试时长当成真人转化率。
