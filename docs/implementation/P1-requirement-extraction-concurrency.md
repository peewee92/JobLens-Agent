# 同岗位要求提取的并发保护

- 用户问题：两个页面同时提取同一岗位时，先完成的结果已保存，较慢请求仍可能在之后保存并被当作最新结果，用户没有机会检查冲突。
- 目标：每次提取记录开始时的最新提取标识；在保存事务内同时验证岗位状态、描述和该标识。如果另一请求已保存，较慢请求不再写入，提示先查看已有结果。两个从相同状态开始的请求最多一个写入，不承诺按发起顺序决定胜者。
- 不做：不取消模型请求、不自动重试、不清理历史、不创建新锁服务、不改变质量审核基线。调用已经发送时费用和轨迹可能已产生；失败时不能虚报完整副作用计数。
- 契约：HTTP 409 `requirement_extraction_superseded`；批量执行逐项返回原因并继续其他岗位；网页展示查看现有结果的指引。
- 验证：隔离 SQLite 在第一个提取计算期间插入另一个实际提取，并检查第一个返回冲突且不能保存；正常连续提取仍成功；批量隔离和页面文案单独验证。只使用离线替身。
- 决定：使用已有短写事务及明确的输入版本，而不是把模型调用放进事务或声称恰好一次执行。OpenSpec 未安装，采用本需求卡。
- 面试口述：在慢调用前记录当前版本，写入时通过事务检查，能防止过期请求覆盖，但不能撤销外部请求，也不能保证发起顺序。

## 验证与边界

- 两个线程使用同一隔离 SQLite、实际应用服务与两个独立事务，同时从相同旧版本开始；实测一个保存、一个冲突，总数只增加一条，新结果可读取。
- HTTP 错误映射与批量失败隔离分别经测试；浏览器通过模拟错误码回跳验证提示，不等同于双标签页真实并发验收。
- 基线策略没有改动：目前旧最终决定仅保存摘要，审核页还依赖当下岗位描述和当前版本，无法直接证明失效样本的完整历史审核内容。要减少连带阻断，需先保证新审核快照和决定原子冻结，再明确旧决定的兼容策略；不能直接把旧基线强行视为有效。
