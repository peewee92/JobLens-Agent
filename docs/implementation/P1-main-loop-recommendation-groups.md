# 主闭环 2C：推荐分组与目标建议边界（2026-10-25）

## 需求卡

- 用户：希望判断先投入哪些岗位、并确认少量目标的求职者。
- 原行为：网页把除 blocked 外的全部报告列为优先候选；图也直接截取前 N 项，low 可能被默认推荐。
- 目标：优先投入（strong/good）、挑战／待核实（stretch）、证据不足（low）、暂不建议（blocked）四组；默认目标最多三个，不以 low/blocked 补位。
- 只有挑战岗位时明确说明；没有可靠建议时给核实入口，不生成空洞 Top 3。
- 默认建议三个，显式请求最多五个；人工最终确认最多五个，分析范围最多五十个。
- 展示所有本轮最多五十个已分析岗位；现有反馈、关注岗位定位和历史链接保留。
- 不做：新模型、匹配概率、运行存储重构、多 Agent。
- 契约：已有 recommendation 是后端业务事实；四组是枚举的展示映射。图只在合法建议枚举中选目标，不改写业务算法；完整排序引用仍保留用于恢复校验。
- 失败：证据不足返回明确阻断与修复入口；越界确认拒绝；旧历史不改写。
- 验收：两种图适配器的 low／混合／挑战／缺少推荐类型场景；确认数量边界；网页分组和默认建议测试；隔离合成数据浏览器验证。
- OpenSpec 未安装／初始化，使用轻量卡；不安装、不提交、不推送、不访问收费模型。

## 技术决策

读取排序和默认推荐不是同一件事：低证据报告仍可查看和人工反馈，但不会因为位置靠前被自动当作目标；保留全量报告指纹，不能只为过滤 low 而削弱恢复校验。

## 可复现失败

只有 low 的输入：旧代码将第一个岗位作为 proposed_target_job_ids，并停在确认页。修复应返回 target_evidence_insufficient，提案为空，仍保留报告引用和核实入口。

## 面试口述

我把“没有硬冲突”和“值得推荐”拆开。匹配报告可以保留未知和差距，排序可以展示全部结果，但默认目标只选有业务依据的积极或挑战建议。系统宁可明确说目前没有可靠建议，也不会为了填满三项制造推荐。


## 实施内容

- 网页四组保留本轮全部可读结果，不再把 low 称作优先候选；目标建议最多三个，精确链接到保存的报告。
- 关注岗位新增证据后，显示实际分组，不再无条件宣称“进入优先候选”；偏好冲突单独展示，不提示用补技能证据解决薪资冲突。
- 两种图适配器只从 strong/good/stretch 产生默认提案；low 不补位，完整排序和报告指纹仍保留。
- 新增 `targetSuggestionMode` 展示提示，只有挑战时明确说明；该字段不替代报告事实或决定状态迁移。
- API、图和人工确认收敛到默认三、最多五、范围五十；旧的 6–10 明确拒绝。
- 网页从实际有报告的岗位里编辑目标，最多五个；非默认建议加核实提示。阻断在刷新恢复后仍保留人能理解的原因和修复入口。
- 三份公开运行请求／状态契约加入共享目录，同步测试防止 Python 形状漂移，网页消费集中状态类型。
