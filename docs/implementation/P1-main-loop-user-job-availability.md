# 用户标记岗位失效

## 需求卡

- 用户：打开岗位后发现不再适合或疑似已失效，希望排除当前推荐，但保留以前的求职记录。
- 行为：用户可显式标记失效，也可恢复为待核实；这是个人标记，不是招聘网站实时状态。重新导入不覆盖标记。排序、报告当前性、等待目标确认的恢复和已保存分析的当前性会复核该标记；更新预检阻断该岗位。旧报告、材料和工作区保留。恢复后仍按现有输入和质量检查判断，不代表岗位真实有效。
- 一致性：单库条件更新按修订号比较；同一标记紧邻的重复请求可重放，旧修订与相反标记冲突。页面只在用户点击时写入，结果不确定时提示刷新核对，不自动重试。这个标记不是通用命令回执，没有历史事件日志。新增匹配入口的保护及其限制见下方补充切片。
- 契约：详情返回 `userMarkedInactive`、`availabilityRevision`；独立 PUT 请求和响应见共享契约。历史报告增加 `job_user_marked_inactive`。迁移为旧岗位设置未标记，不推断其是否正在招聘。
- 不做：自动判断关闭、网站查询、修改原始招聘记录、自动恢复、删历史、真实模型调用。
- 失败例证：用户确认目标后标记其中一个岗位失效，旧实现没有任何持久状态可供恢复验证，仍可能继续生成当前材料。现在排序重验后该运行进入过期状态。
- 技术决策：用户标记附着岗位而非来源采集记录，避免重新导入撤销用户决定；复用既有报告当前性和最终事务内复核，不建设另一套 Agent 状态。

## 验证与边界

- 真实 SQLite / HTTP 测试覆盖相同请求重放、旧修订冲突、并发相同请求、失效后排序只排除该岗位、等待确认转过期、历史分析保留、恢复后复核、更新预检阻断和重新导入不恢复。注入数据库更新失败时返回可重试错误且原标记未变，再次操作可成功。
- 将已有隔离合成库从迁移 0028 升级至 0029；没有迁移真实求职库。自动迁移测试另覆盖旧岗位默认值、升级与降级数据保留。
- 浏览器在隔离库实际标记、查看历史报告不再为当前、导入批次仅保留另一岗位进入分析，并恢复该标记；不表示真实岗位已关闭或真实模型质量已验收。
- 最终代码针对性测试 14 项和新增历史原因契约检查后 4 项通过；网页 292 项、类型检查及 `git diff --check` 通过。后端全量 1683 项通过；全量启动后另增加了执行创建阻断和历史原因契约断言，因此这两项以其后的针对性结果为准，不将全量数字误称为覆盖它们。
- 面试口述：状态来自用户，不等于来源事实。我用条件更新保护多标签页，排序与最终保存复用同一当前性检查；历史内容保留。用户可恢复标记，但系统不会因此声称招聘网站仍开放。

### 补充切片：旧匹配入口的失效岗位保护

- 范围：单岗位语义匹配、匹配报告、批量匹配；不改变历史报告、人工求职状态和准备材料的读取。
- 已标记失效时，新的匹配在进入语义工作流前返回 `job_user_marked_inactive`；批量匹配逐项阻断，并继续其他岗位。页面提示从岗位详情恢复标记。
- 生成报告时先记录岗位状态修订号，保存前以 SQLite 短写事务锁定并核对；计算期间即使状态先变更再恢复，也返回 `job_availability_changed`，不保存过期报告。模型计算不在事务内。
- 匹配执行期间才发现状态变化时，已发送的模型调用不能撤销；批量响应将副作用计数标记为不完整，不伪称零调用。
- 单独的临时语义匹配只在开始前检查状态，不保存报告；运行过程中已发出的请求无法撤销。后续若要让该临时结果也具备完整版本一致性，需要单独设计返回前校验。
- 验证使用隔离 SQLite、离线替身和接口测试，不访问真实数据或收费模型；不意味着已完成真实用户端到端验收。
