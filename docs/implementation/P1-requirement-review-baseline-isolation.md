# 冻结审核基线与岗位变更隔离

- 用户问题：审核样本中的一个岗位更新，会使其他岗位也失去同版本审核基线，阻断真实求职分析。
- 目标：仅对新格式审核决定，校验完整快照、摘要、决定汇总和模型版本；样本后来改变不撤销其历史审核基线。每个当前岗位仍单独验证描述、要求、执行记录和模型版本，不能因基线存在而放行坏数据。
- 旧记录：两项快照字段均为空时继续现有保守规则；缺少一项或校验失败不得当作旧记录回退。拒绝结论从不成为基线；没有完整证据不推断新基线。
- 边界：不回填旧记录、不更改人工结论、不降低质量门槛、不调用模型；摘要不是数字签名。决定快照不使已变更岗位自身的旧要求变成当前要求。
- 验证：隔离 SQLite 测试新决定样本改变后无关岗位仍可用，变更岗位自身阻断；旧决定仍随样本过期；快照缺失、篡改和版本不匹配均拒绝；确认界面同时说明冻结基线与样本当前性。
- 技术决策：模型版本质量证据和具体岗位当前事实采用不同生命周期；新旧记录不混用，决策快照校验失败时不静默降级。
- 失败例证：旧路径对样本实时当前性作全局依赖，任一审核样本重新导入会撤销全部岗位的基线。
- 面试口述：固定评估证据不能替代每次输入校验；基线证明同版本审核过，岗位事实仍必须分别核对。

## 本轮交付与验证边界

- 新接受决定使用 `schemaVersion: 2` 和 `frozen_cohort_v1`，在确认表单提前说明其含义；版本 1 快照和无快照历史决定仍遵循原有当前性规则，不扩大旧决定的授权范围。
- 冻结快照需通过摘要、决定指纹、案例、版本与审核汇总检查；检查失败不会回退成历史记录。摘要用于发现意外损坏，不是抵御数据库篡改的签名。
- 隔离 SQLite 和接口测试覆盖样本变化、旧决定、坏快照及岗位自身检查；浏览器使用合成数据验证页面对基线有效与样本过期的区分。尚不能据此宣称真实岗位或完整用户主流程已验收。
- 本步骤结束时，既有 `requirement-manual-review-smoke.mjs` 因过时页面文案断言尚未通过；下述后续验证已修复该问题。

## 后续：临时数据库完整接口冒烟

- 修复过时的页面文案断言，保留接口原因码和人工决定的检查。对临时 SQLite 数据库执行真实迁移，启动 FastAPI 与生产构建的 Next，使用合成数据完成 20 条审核及最终决定。
- 冒烟验证：重提取一个岗位后，基线仍有效、该岗位因版本不一致阻断，另一个未变岗位仍可用；再向临时库注入第二个岗位的执行错误，接口返回 `trace_failed`，基线仍有效。该脚本已通过；这属于 HTTP 与页面服务端渲染验证，不是浏览器点击全流程，也不是真实模型质量验收。
- 可复现失败：旧脚本要求页面暴露 `accepted_baseline_missing` 内部代码，但页面已改为面向用户的修复说明，导致测试误报；现在在接口校验原因码，在页面校验用户可见说明。
- 技术决策：质量基线和岗位执行记录分别检查，不能因审核过的版本存在就放行失败记录。面试口述：用临时数据库注入一条失败轨迹，在不撤销整个基线的同时证明单岗位仍被阻断。
