# 阶段 3B-3：请求重试与服务端找回

## 需求卡
- 用户：开始或确认时断网、刷新、换标签页或丢失浏览器本地引用的求职用户。
- 原行为：开始成功后才存 threadId；确认重试每次新建 actionId；仅靠 localStorage 恢复，无法从服务端找回最近运行。
- 目标：发送前保存规范化完整命令；网络重试沿用原标识及内容；URL 带 threadId；GET 最近运行列表仅查询主权威状态，不自动继续；找回已接受决定后由用户继续。
- 数据边界：本地日志只存标识、岗位范围、数量和人工决定，不存职业全文或密钥；服务端列表不创建第二套进度。
- 异常：本地保存失败不发请求；首次 GET 404 若仍有未确认开始命令，保留重试；已确认状态清理对应命令；不同内容不能覆盖未解决命令；URL 优先于本地最近引用。
- 验收：命令写入早于发送；网络失败重试请求体完全相同；服务端列表无事件增长；清除本地引用后通过最近列表重开；相同 actionId 重试不改写决定。
- 不做：完整结果快照、工作台和反馈仍按原计划继续；不调用收费模型、不修改真实数据库、不提交推送。OpenSpec 未初始化，使用轻量需求卡。

## 技术决策

只在浏览器保存传输命令，不保存另一套业务进度。开始和确认共用同一个“先保存、后发送”函数，恢复后严格比较规范化内容，重试使用读回的同一请求体。未解决命令不能被新决定覆盖；读取时只允许有限结构字段，不保留职业全文。不同运行的日志按 threadId 隔离。

服务端最近列表直接读取主运行表，排序有稳定的 threadId 次级键；URL 优先于浏览器最近引用。本地存储不是跨标签页锁，真正的确认竞争、修订检查和执行权仍由数据库保证。不同页面决定已被接受时清理过期传输命令，并明确告知以服务端结果为准。

## 可复现失败

在岗位页面加载成功后停止隔离后端，再开始分析。旧实现既没有保存 threadId，也没有保留请求内容；恢复服务后会生成另一套标识。新实现发送前已写入原命令并更新地址；恢复服务及刷新后，GET 404 不丢弃未确认开始命令，点击“重试原请求”只创建一个运行。

实际浏览器测试还发现同源代理未转换连接异常，返回笼统 500。现统一转换为 503 backend_unavailable，并提示先查看状态再重试原请求；不把无法确认结果当作“请求肯定没执行”。

## 面试口述

网络失败不能证明服务端没有接受请求。我把命令在发送前保存下来，重试时保持标识与内容不变；先查询状态，再决定是否重发。恢复入口有地址和服务端最近列表，不依赖浏览器存储作为唯一依据。浏览器日志只负责传输，数据库运行记录才是状态真相。

## 后续范围保留

下一阶段 3C 保存有类型的分析和准备结果，固定工作流消费的事实版本，并在最终短事务重新检查，避免实时计算页面冒充历史结果。之后继续任务工作台、一键工作区、统一事务、确认事实与限定范围更新分析、结果比较和三条完整用户路径。当前不宣称全部目标完成。
