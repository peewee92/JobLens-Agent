# 分析前区分可排序与可提出目标

## 需求卡

- 用户：准备对已选岗位启动分析的人。
- 原行为：只要有可排序报告就允许启动，即使所有报告均为证据不足，运行仍会被 `target_evidence_insufficient` 阻断。
- 目标：预检区分“进入排序”和“可以提出目标建议”。证据不足的岗位继续可查看，提供岗位与依据入口；全批无候选时不创建注定阻断的运行。
- 不做：不伪造推荐，不把缺少证据当成不具备能力；不新建匹配，不更改报告或事实，也不替用户决定补充事实。
- 契约：排序响应新增 `targetCandidate`，由图编排相同的后端 `is_target_candidate` 计算；共享结构为 `batch-match-ranking.schema.json`。MCP 保持显式字段过滤。
- 失败边界：缺少或格式错误的字段不允许启动；旧后端需升级后才能通过新前端预检。预检只是快照，正式运行仍重新检查，已有请求重试不受影响。

## 技术决策与失败复现

后端输出规则结果，而不在网页复制 `strong / good / stretch` 枚举判断，避免将来出现规则分叉。使用隔离数据库，将一个有效报告设置为 `low`：它仍能进入排序，但不能提出目标建议，页面保留详情链接并禁用运行。无候选不代表无能力或岗位不适合。

## 面试口述

“可排序和可作为目标不是同一回事。我把图里已有的确定性规则投影到排序响应，页面提前解释缺少依据，避免创建必然阻断的分析；真正执行仍以服务端当时的事实为准。”

## 证据不足入口的浏览器补充验证

在独立合成数据库副本中，人工构造一个 `low` 匹配报告并保持岗位范围为一项。浏览器点击检查后，页面显示岗位可查看但证据不足以提出目标建议，说明这不代表用户不具备能力，运行按钮保持禁用；点击岗位入口可查看报告的“证据不足”和待核实说明，并保留返回原分析范围的链接。该报告是人为构造的呈现夹具，且岗位页实时资格判断仍依据原资料计算，因此不能证明真实缺失证据的端到端生成或补充事实后重新匹配；这些仍需单独验证。
