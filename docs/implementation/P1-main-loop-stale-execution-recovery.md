# 主业务闭环：执行前事实变化的恢复

## 需求卡

- 用户：打开已保存的分析后，在其他页面或标签修改资料，再尝试将分析用于工作区。
- 原问题：服务端明确拒绝过期事实后，网页仍保留原请求并反复提示重试；同一个请求无法产生新材料，用户被困住。
- 行为：仅当接口返回与原命令标识一致、不可重试的 `analysis_execution_facts_stale` 时，清除匹配的本地待处理请求、阻止以旧分析新建材料，并引导用户检查输入及更新分析。其他标签的新请求不得被清除。
- 不做：不清除网络故障、服务异常、其他拒绝或无法关联的响应；不改业务记录、协议或调用模型。
- 契约：沿用已有错误响应的原因码、可重试标志和关联标识；SQLite 执行事务先读取命令回执，再检查事实版本。

## 验证与面试表达

真实浏览器使用隔离的合成数据库副本：打开有效分析后，仅在副本模拟资料版本变化，再点击应用；服务端拒绝，页面提供更新入口并禁用旧分析，刷新后不再显示旧请求重试。前端测试覆盖响应身份与网络故障边界。此场景只证明这一恢复路径，非完整三条用户路径。

决策：明确的业务拒绝与发送后结果未知的网络故障必须分开处理；前者依据服务端确认收尾，后者保留原始命令以安全重试。失败例证：旧页面在收到过期拒绝后始终显示“重试原请求”。
