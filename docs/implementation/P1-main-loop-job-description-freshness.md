# 岗位描述变化后的历史报告与排序

## 需求卡

- 用户：重新采集岗位后，历史报告仍可查看，但不应把基于旧岗位描述的结论当成当前推荐。
- 原问题：岗位要求发布检查按原文指纹判断过期，匹配报告和排序只比较提取记录 ID；描述变化但旧提取还是最新记录时，旧报告仍可进入当前排序和分析。
- 行为：匹配报告的当前性同时检查岗位详情的描述指纹与提取输入指纹。不同则标记 `job_description_changed`，排除当前排序，并通过现有分析快照版本检查标记历史材料。历史原报告和已保存材料不变。只有首尾空白变化不视为变化，与现有提取校验一致。
- 不做：不自动提取新岗位要求、不删除历史、不将较短描述判断为岗位失效、不调用模型；岗位原文更新仍由现有导入规则决定。
- 契约：匹配报告历史 `staleReasons` 增加 `job_description_changed`；排序预检和已保存分析继续使用现有字符串原因数组。Web 展示中文原因；未知码有安全回退。
- 技术决策：复用岗位要求提取已保存的输入指纹，而不是新建第二份岗位版本状态；后端只在读当前岗位详情时核对，历史数据保持不可变。

## 验证与口述

- 可复现失败：已存在一份匹配报告；仅更新岗位描述，不创建新的提取时，旧判断因提取 ID 未变化仍将报告列为当前；要求发布检查实际已报 `extraction_input_stale`。
- 后端：真实 SQLite 和 HTTP 的合成测试验证重新导入同一岗位后，旧报告不再进入排序、历史内容不变、导入快照保留；另验证已保存分析变为历史、同范围其他岗位仍可排序、首尾空白不触发过期、只读检查不调用模型，以及新增原因符合共享契约。相关测试 53 项和新增契约测试通过。
- 前端：类型检查、285 项测试通过；隔离示例库浏览器实际显示“历史结果：不再用于当前排序”和“岗位描述已变化，需要重新分析岗位要求”。未验证真实招聘网站采集或真实模型提取。
- 面试口述：同一份提取记录的 ID 不变，并不代表它的原始输入没有变化。我把提取时的输入指纹接入排序和历史判定，既阻止旧结论污染当前推荐，也保留用户之前看到的历史结果。

## 目标确认与计算期间的变化

- 目标：用户确认目标前或计算进行中岗位描述改变时，停止将旧依据作为当前分析；用户刷新后能知道原因，并回到原岗位范围排查。
- 已验证：真实 SQLite/HTTP 路径中，等待确认时修改描述再确认，运行进入 `stale`，不生成分析材料；计算完成但提交前修改描述，运行标为 `stale`，已保存材料只能作为历史查看。两条路径未调用模型。
- 界面调整：过期状态不再笼统称为“职业资料变化”，而是说明岗位或匹配依据也可能变化，提供返回原范围的入口。曾复现客户端路由只更新地址、不重置运行的问题；采用完整页面导航后，在隔离浏览器中确认两个原岗位重新勾选，预检明确指出变化的岗位。
- 口述：人工确认不是永久授权。确认后还要重新验证事实，计算期间的变化通过最终保存前校验识别，避免把旧输入计算出的材料标为当前；如果材料已经算出则保留为历史，而不伪造一次成功。

## 无法读取完整描述时不复用报告

- 可复现边界：排序仓库应返回岗位详情，但若错误地只返回不含描述的岗位列表条目，之前的类型分支会跳过指纹检查，错误地视为报告仍可用。历史提取缺少输入指纹同样无法证明当前性。
- 处理：对两种输入不充分情况标记 `job_description_unavailable`，不推断岗位已经变化，也不允许进入当前排序；其他可核实岗位不受影响。该原因已加入历史报告共享契约及中文说明，不改变数据库。
- 验证：模拟错误仓库投影的真实 SQLite/HTTP 预检显示一个岗位不可核实、另一个仍可排序；浏览器实际显示中文原因。相关后端回归 74 项、额外集成测试 7 项通过；前端类型检查与 287 项测试通过。示例数据及注入只存在隔离进程，不调用模型。
- 面试口述：缺少核实信息既不是“已变化”，也不是“没变化”。高风险推荐应保守停止复用，同时保留其他输入正常岗位的可用性。
- 更大范围回归：在独立临时 SQLite 数据库、旧检查点库隔离且所有模型提供方禁用的条件下，完整后端测试 1677 项通过。此前 5 项偏好测试使用了缺少输入指纹的旧替身，已补齐与真实提取一致的指纹后重新验证。
