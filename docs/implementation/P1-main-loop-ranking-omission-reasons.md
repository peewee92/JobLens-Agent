# 分析前说明岗位未进入排序的原因

## 需求卡

- 用户：已选岗位未能进入默认排序，需要知道如何继续的人。
- 原行为：页面统一列出多个可能原因，不能知道哪个适用于当前岗位。
- 目标：以只读快照逐岗位区分尚无报告、报告过期、当前报告明确硬冲突，并展示可识别的过期原因及岗位详情入口。
- 不做：不自动更新报告、不补充职业事实、不调用模型，不声称实时岗位有效，也不保证快照之后事实没有变化。
- 契约：`GET /api/v1/match-ranking/preflight` 接受 1–50 个互不重复的岗位；共享结构为 `ranking-preflight.schema.json`。完整旧排序接口与 MCP 输出保持兼容。
- 失败边界：报告不存在只说明没有查到报告，不说明岗位无效或用户不具备能力；未知过期原因展示为其他事实变化。响应缺项、重复项或格式错误不允许开始分析。

## 决策和复现

预检与正式排序复用同一后端评估过程，避免两个判断分叉。预检是多次只读查询的结果，并不是数据库级跨查询快照：并发修改可能影响检查结果，所以正式执行依旧重查。复现：用隔离数据库选取一个无报告岗位和一个资料版本变化的岗位，检查时分别显示“尚无匹配报告”和“职业资料已更新”。

## 面试口述

“我没有让网页猜测缺失原因，而是在原排序用例中复用同一套当前性判断，返回有边界的原因码。预检不做写入或付费调用，也不把它当成并发一致性的替代品。”
