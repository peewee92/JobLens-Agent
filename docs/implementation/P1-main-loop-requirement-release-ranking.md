# 岗位要求失去可用资格时停止推荐

## 需求卡

- 用户问题：岗位要求原文和版本没变化，但提取记录的校验轨迹出错或要求不再满足发布条件时，旧匹配仍会进入排序和目标确认，直到准备材料阶段才被拦截。
- 目标：排序与匹配历史复用现有岗位要求发布检查；未通过时保留原报告作为历史，显示明确原因，并排除当前推荐。人工确认前的重复排序自然重新检查，其他通过检查的岗位仍可排序。
- 契约：历史原因增加 `requirements_not_released`；排序预检沿用 `report_stale` 及字符串原因，网页给出核对入口。MCP 复用同一业务排序，不增加第二套逻辑。
- 不做：不删除或改写历史、不自动重提取、不调用模型；这不是跨所有检查的原子快照。最终提交仍由现有事务内版本及资格复核保障。
- 可复现失败：隔离 SQLite 将一条合成提取轨迹标为失败后，输入就绪接口已阻断，而旧排序预检仍返回该岗位。其他岗位不受影响。
- 技术决策：沿用现有发布检查，不能仅凭提取记录 ID 或输入指纹声称其可用。轨迹出错、人工基线变化或要求记录不一致都应保守停止新推荐。
- 已发现的限制：审核基线包含的一个样本发生变化时，现有基线查询可能撤销整批基线，导致其他岗位也无法通过发布检查；这不是单岗位隔离。旧路径在准备材料阶段本已受同一检查阻断，现在会在排序阶段提前暴露。需要后续重新设计审核基线的生命周期与用户修复入口，不应简单绕过检查或承诺其他岗位必然可用。

## 验证与口述

- 隔离 SQLite 和真实 HTTP：一条岗位的合成提取轨迹被标记失败后，该岗位退出排序、原报告保持不变并标为历史，另一条仍可排序；在等待确认后制造同一故障，确认会进入过期状态，不保存结果。共享历史契约已验证新原因。
- 浏览器：隔离合成数据中对两岗位执行预检，显示一项可排序，另一项给出中文检查原因和岗位链接；不运行模型。
- 全量回归：隔离环境、模型提供方禁用时，后端 1679 项、网页 289 项通过；网页类型检查和 `git diff --check` 通过。尚未验证真实岗位、真实模型、实际并发或大批次读取性能。
- 面试口述：历史报告的输入版本一致，不等于它当前仍有可使用的要求依据。我让排序、确认恢复和历史展示复用已有发布检查；旧报告保留，禁止把不再可信的依据当成当前推荐。全局基线仍可能带来连带阻断，不能以测试通过掩盖这一产品限制。

后续增量：`P1-requirement-review-baseline-isolation.md` 为新版本 2 审核决定引入经明确授权的冻结基线；旧决定仍可能因样本变化而整体失效。无论哪种基线，当前岗位仍需单独通过事实与执行记录检查。
