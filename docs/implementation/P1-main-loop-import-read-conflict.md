# 导入页：读取结果不一致时不猜测

## 需求卡

- 用户问题：导入页分别读取已保存匹配、匹配输入和岗位要求状态；这些不是同一个数据库快照。如果读取失败或期间事实变化，结果可能矛盾，旧页面仍可能把岗位列为已匹配或可匹配。
- 行为：仅当排序、匹配输入和要求状态均可读取且互相支持时，岗位才进入已匹配或可匹配范围。已排序与阻断／未知冲突，或匹配输入可用与要求阻断冲突时，显示“暂时无法确认”，不列入分析入口、匹配计数和反馈队列。未排序且要求受阻、没有与之矛盾的可用输入结果时仍显示要求未准备。
- 边界：这只是只读页面的保守汇总，不是跨请求原子快照；即使读取一致，后续操作仍必须由服务端重新检查。读取失败可能暂时隐藏可用报告，用户可以刷新或查看岗位。没有重算或修改业务记录。
- 验证：组件逻辑测试覆盖冲突、缺失和正常状态；网页全部 289 项测试、类型检查和 `git diff --check` 通过。在隔离合成库副本上，测试代理只将一条岗位要求响应改为阻断，另外保留其匹配输入和排序的真实只读响应；浏览器显示一条待核实、一条已匹配，分析入口只含后者。该注入不是实际并发测试，也不是完整业务闭环。
- 失败例证：同一岗位已有排序结果、匹配输入可用、要求检查为阻断时，旧代码先返回 `matched`，并将其放入分析入口；现在不推断哪次读取更新。
- 面试口述：不同接口的成功响应并不自动组成一致快照。我把相互矛盾的结果保守地作为未知，同时保留其他岗位的正常路径；真正的事实一致性仍由执行前服务端验证，而不是由页面声称解决。

## 后续纠正：采用实际匹配规则

最初版本错误地将严格的正式质量验收接口与实际匹配输入接口视为同一规则。对于明确允许的冻结版本，前者可以阻断而后者允许，属于合法差异，不能当作竞态。现改为只使用匹配输入接口返回的内嵌岗位要求状态，排序和匹配输入之间仍作保守冲突判断；岗位详情也采用同一实际匹配规则，并明确不把可匹配称为正式模型质量验收通过。减少了一次逐岗位请求，不改变服务端规则。

隔离数据库副本中，构造无正式基线但符合冻结版本规则的两个合成岗位：严格接口阻断、实际匹配接口允许、排序返回两项；浏览器导入页显示两份已匹配，岗位详情明确“符合当前匹配规则，但不代表正式模型质量验收完成”。另以测试代理让一项匹配输入响应与排序冲突，页面仍只将该项列为待核实，其余岗位可用。数据是测试夹具，代理注入不等同实际并发。
