# 主闭环 5B：真实成果提案与显式重新核对

## 需求卡及完成标准

- 用户：完成简历核对、面试准备或学习行动后，确实获得了可引用的新成果，需要自己提出并确认，而不是系统推断能力。
- 目标：从行动原始分析/要求版本读取可关联技能要求；用户选择具体要求、填写真实事实并核对当前资料版本。保存提案不改 Profile，确认才生成新版。行动来源和当前确认基准分别保存。
- 旧提案过期：保留旧提案，不改原文或来源；用户明确核对当前资料后建立替代提案。替代链只允许一次事实确认，不自动合并、升档或推断排名改善。
- 事务：沿用 5A；一个 Session 检查当前版本、来源与幂等再写入。网页请求在发出前保存，不确定失败沿用原请求，刷新可查找。
- 接口：扩展已有提案请求/响应，增加只读证据上下文与显式重新提交接口。共享契约同步。模型调用为零。
- 验收：普通准备行动真实提交→待确认→确认新 Profile；更新分析后的行动不误用工作区最初资料；过期重新核对保留旧提案；并发与网络重试不重复确认；历史材料不被覆盖。测试使用隔离 SQLite 和合成资料，浏览器验证。
- 不做：限定范围再分析/结果比较（5C）、自动事实确认、自动模型调用。保留所有未提交工作，不提交推送。OpenSpec 未安装/初始化，采用本卡。

## 本轮实现（2026-10-26）

- 普通简历事实核对/面试准备行动现在可提交成果，选项来自行动原始分析绑定的 `JobRequirement`，不重新读取 JD、不调用模型。
- 行动原始 Profile/分析/提取版本与本提案核对的当前 Profile 分列。新分析复用旧工作区时，新行动不会误用工作区最初资料；真实接口测试覆盖 v1 工作区与 v2 新行动。
- 新提案保存请求内容摘要。相同标识同内容返回原回执，摘要、来源、选择的要求、核对版本或确认选项变化均冲突。提案创建不改资料。
- 旧提案不能跨版本直接确认。用户显式核对后创建新提案，原文及来源不变；同源提案在同一短事务内检查确认状态。同源并发确认只接受一个。
- “暂不判断”不覆盖已有技能程度。选择一项要求只绑定该项，不把一次用户声明扩张到行动的全部要求。
- 网页事实请求先暂存再发送；未知失败保留原请求；刷新不执行写入；已知拒绝允许明确丢弃后修正。它不是锁，不承诺浏览器跨标签页互斥；服务端幂等和版本/事务检查才是最终保护。
- 被替代或同源已确认的旧提案保留为历史，不再计入待处理数。否则会出现“还有一项待确认但无可用按钮”的错误指引。
- 保留原有零模型单岗位匹配入口，不冒充范围再分析或新保存结果。

### 验证中发现并修复

1. 首轮新接口测试发现项目序列化默认使用驼峰键，重新核对命令不能将默认 `model_dump()` 直接传给 Python 方法；改为明确 `by_alias=False`，实际接口与并发测试复验通过。
2. 选择要求后曾仍保存行动的全部要求 ID；改为只保存用户实际选择项，并增加多要求单元测试。
3. 浏览器看到旧提案被替代后仍被计为待确认；修正只读汇总及历史标签，增加实际接口与相同时间戳的稳定选择测试。
4. 全量回归首次发现旧汇总测试用仅含 `status` 的假对象，无法表达来源链；测试改用真实提案模型，不在生产代码中用动态缺省掩盖类型缺失。全量复验结果另见下文。

## 技术决策

**另存重新核对提案，不原地修改来源版本。** 代价是多保留一条记录并在汇总中识别来源链；收益是可以解释“当时基于什么资料、后来核对了什么”，避免把旧行动和旧人工声明伪装成当前事实。沿用现有同库事务，不新建通用事件平台或另一个运行状态机。

## 可复现失败

仅在隔离数据库执行：

```sql
CREATE TRIGGER fail_feedback_event BEFORE INSERT ON application_timeline_events
WHEN NEW.event_type = 'evidence_confirmed'
BEGIN SELECT RAISE(ABORT, 'synthetic final event failure'); END;
```

确认提案应返回结构化 503；数据库仍只有原资料版本、提案未确认、无确认事件。刷新页面应保留原请求但不自动 POST。删除隔离故障触发器后点击“重试原事实操作”，只生成一个新版本和一个确认事件。对应自动回归：`test_confirmation_last_event_failure_rolls_back_profile_and_proposal_then_safe_replay`。不要在真实求职库执行此故障注入。

## 面试口述

> 我把行动完成和能力事实分开。完成准备不会自动增加能力，用户要指出具体岗位要求、填写可追溯成果并核对当前资料。行动最初来源和本次确认基准分开保存。资料变了就另存核对提案，不篡改历史；同源只确认一次。浏览器保存原命令用于网络恢复，真正的一致性保护仍由服务端短事务、版本检查和幂等承担。我用 SQLite 最后一步故障和并发确认验证边界，而不是只展示成功状态。

## 后续拆分及未完成范围

1. **5C-1：限定范围更新。** 从原结果选定同一批/目标岗位（最多 50），查询当前事实、可复用报告/提取和缺口；显式继续，每次最多处理 5 个新增分析，单岗位失败保留其他成功结果。复用原运行存储/领取机制，不能新建第二套权威进度。
2. **5C-2：新旧结果比较。** 绑定当前资料/意向及固定要求版本，保存新运行和结果，原结果不覆盖。同一岗位范围比较实际理由、未知与冲突；允许未变或变差。旧单岗位匹配路径要收敛到相同应用边界，当前仍用工作区初始要求定位，不足以代表新分析的全部来源。
3. **5C-3：页面闭环。** 在原结果和工作区提供真实“更新分析”入口、预检、继续/修复与比较，不用跳转实时差距页替代历史结果；补齐投递/行动命令的浏览器恢复。模型无授权时零调用，需语义判断则明确等待。
4. **阶段 6：完整验收。** 以正常、证据不足、故障恢复三条主流程做贯穿浏览器验收；真实数据副本做业务验证。新真实岗位及收费模型必须单独授权，当前没有授权，未执行。
