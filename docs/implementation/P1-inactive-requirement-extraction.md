# 失效岗位的要求提取保护

- 用户与问题：用户已经标记失效的岗位，不应从单岗位或批量入口启动新的要求提取并产生潜在模型费用。
- 目标：提取前检查状态；计算后在保存事务内检查同一状态修订，状态变化时不保存新提取；批量任务逐项说明问题，其他岗位继续。历史要求与人工求职记录保留。
- 边界：不取消已发出的模型请求，不更改失效标记，不假设状态即招聘网站的真实状态。模型调用在事务外进行，计算中变更时副作用计数不能虚报完整。
- 契约归属：后端应用服务及 API 错误码 `job_user_marked_inactive`、`job_availability_changed`；批量结果复用现有逐项错误码和计数完整性字段。
- 验证：隔离 SQLite 上单岗位接口无调用、计算中标记／恢复导致回滚、正常岗位依然可保存、批量继续；不使用真实数据或收费模型。
- 技术决策：复用应用层状态和 SQLite 短写事务，不在模型调用期间持锁；保证本地单库下检查与写入的一致性，不声称可撤销外部调用。
- 可复现失败：旧路径在已标记失效后仍可进入要求提取；现在应在执行模型前返回明确阻断。
- 面试口述：把外部调用移出事务，再用版本复核与本地数据库写锁保护保存边界；被拒绝的结果可能已经产生外部调用，因此费用统计必须诚实表达不确定性。

## 本轮验证

- 在隔离 SQLite 的 HTTP 测试中，失效岗位返回 409，提取工作流未调用，历史提取仍可读取；提取计算期间失效并恢复时返回状态变更，未保存新提取。
- 在浏览器使用隔离合成库和离线替身，验证失效时按钮禁用并提示恢复；恢复后能够提交，保存新提取，旧匹配报告显示岗位要求已更新。
- 离线替身的新提取仍显示没有有效审核基线，不能直接用于正式匹配；这只是离线功能验证，不是模型质量或真实岗位验收。
