# 阶段 3A：同库运行状态与原子迁移（2026-10-25）

## 需求卡
- 原行为：正式运行使用第二个 SQLite 文件，save 无条件覆盖；并发确认可能相互覆盖，状态事件按完整 payload 去重。
- 本切片：正式运行改用现有 SQLAlchemy SessionLocal；Alembic 增加运行及追加事件表；状态迁移检查原状态、步骤、修订和身份，并与事件同事务提交。
- 旧文件只读保留：已完成运行明确没有原始结果快照；未完成运行要求重分析；不双写、不在 GET 自动建表或执行业务。
- 旧 SQLite 适配器保留给历史读取及冻结测试；正式执行不调用其任意 save。
- 不做项：本切片不声称执行恰好一次；命令摘要、执行租约、显式 Continue、有类型结果和最终事实版本校验紧随其后。
- 验收：真实 SQLite 并发迁移只有一个胜者；事件失败整体回滚；重启重开；缺迁移返回可修复错误；旧文件哈希不变；生产依赖确实使用同库实现。
- OpenSpec 未安装／初始化，使用轻量需求卡；保护所有未提交工作，不调用收费模型、不触碰真实数据库。

## 技术决策
运行权威状态和追加事件放进同一短事务。状态迁移返回新的修订，调用链必须继续使用返回值，不能继续拿旧修订保存。图仍负责排序编排，应用服务负责数据库边界。

## 可复现失败
两个请求读取同一等待确认状态，分别 approve/reject。旧 save 会让后者覆盖前者；条件更新应只允许一个提交，另一个明确冲突，且不能新增虚假成功事件。

## 面试口述
我没有因为使用 LangGraph 就把恢复问题交给框架假定解决，而是明确了权威状态和事务边界。数据库以修订和预期阶段做条件更新，状态与事件一起提交。它解决的是覆盖和部分提交，不是外部模型恰好一次；执行领取和结果不确定是后续独立机制。

## 明确边界与下一切片

1. **3B 命令与执行保护**：请求内容摘要、相同标识不同内容冲突、短租约与过期执行者保护、显式继续、服务端最近运行及网页重试标识。验收重复提交、两个执行者竞争、租约过期、刷新与重启后继续；GET 不启动工作。
2. **3C 保存原始结果**：差距及准备工作流消费固定事实版本；保存有类型的结果与完成状态同事务提交；最终短事务重验事实版本，重开历史结果不重新计算。
3. 然后进入工作台和一键工作区，再做确认事实及限定范围更新分析。每次交付可观察切片，不先扩图、换框架或增加后台调度。

本轮的条件更新防止状态覆盖，但不防止所有重复计算，也不承诺模型恰好一次。现有完成状态仍不能替代完整差距／准备结果快照。旧文件仅提供最近状态的只读历史投影，没有导入旧事件：已完成旧运行明确无原始快照；未完成旧运行要求重新分析，不能用新规则静默继续。以上不足不以测试数量掩盖。
