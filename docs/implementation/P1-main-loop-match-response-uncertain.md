# 批量匹配响应不确定时先核对

- 问题：批量匹配可能已逐岗位保存报告后，客户端遇到网络错误或服务端错误；原界面将其描述为失败并直接提供重试，可能重复创建报告。
- 本轮：网络异常、解析异常、HTTP 408 和 5xx 显示“结果暂时无法确认”，隐藏直接提交按钮，提示刷新并检查已保存与待处理岗位。明确的其他客户端错误仍保留原错误信息。刷新只读取已有状态，不自动重算。
- 范围：这是当前页面的保守交互保护，不是服务端幂等。用户在请求仍执行时主动刷新、打开另一标签页或直接调用接口仍可能重复执行；刷新时运行尚未结束也可能尚未看到结果。后续需要持久命令标识、领取和服务端重放机制。
- 验证：网页类型检查和 302 项测试通过。对隔离 SQLite 副本迁移后，使用离线替身，测试代理先将请求转发给真实后端、待成功响应后返回 503；浏览器实际显示结果不确定且没有再次提交按钮。点击刷新后，已保存匹配数从 1 增至 2，新增岗位可进入分析。故障是本地代理注入，不代表真实网络测试或完整求职闭环。
- 失败例证：服务端成功保存后代理丢弃响应，旧提示“匹配失败，请……重试”错误暗示没有保存。
- 技术决策：区分已知失败与未知结果；不以界面保护声称服务端实现了恰好一次。
- 面试口述：客户端没有收到响应不等于事务回滚。我先阻止界面直接重发，并通过刷新重新读取事实；要解决多标签页和服务端竞态还必须加入持久幂等与执行领取。
