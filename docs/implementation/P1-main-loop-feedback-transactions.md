# 主闭环 5A：反馈与职业事实的原子保存

## 需求卡

- 用户：完成行动后人工提交并确认真实新成果，或记录投递与行动状态。
- 原问题：各仓库自行提交；Profile 已保存而提案确认/事件失败时留下半份结果；状态变更与事件也可能分离。
- 本片目标：生产 HTTP 写入口复用原业务用例，但由调用方一个 Session/工作单元整体提交。Profile、提案确认、确认事件必须全有或全无；状态与对应事件同样原子。重复确认只返回原确认，不再创建 Profile；并发不同决策仅允许一个成功。
- 输入输出：保持既有接口形状。数据库保存失败新增可重试原因码，原子回滚后可刷新/重试。不新增模型、不自动确认事实、不修改真实数据库。
- 不做：通用产物平台、跨库事务；准备行动产生一般事实的提案入口与来源版本改造留到 5B；更新分析和结果比较留到 5C。
- 完成标准：真实 SQLite/API 注入最后一步失败后 Profile、提案、事件不出现部分提交；恢复后重试一次成功、重复及并发确认不重复升版；行动和投递事件故障回滚；既有业务回归通过。
- OpenSpec 未安装/初始化，使用轻量卡。所有既有未提交文件保留。

## 本轮实现

- 生产环境的创建事实提案、确认提案、修改行动状态、修改投递状态四个入口，由 `TransactionalWorkspaceCommand` 组合原用例；`SqlAlchemyWorkspaceCommandUnitOfWork` 提供同一个调用方 Session，最后只提交一次。仓库不提交调用方事务，退出时统一回滚/关闭。
- Profile 保存增加 `execute_in_repository`，复用原校验和版本规则，不在确认事实时开启内层事务。常规 Profile/SearchIntent 写工作单元也在 SQLite 使用短写锁，避免两个入口同时读旧版本后争抢升版。
- 行动/工作区状态改为数据库条件更新；当前状态不符不能覆盖。行动已经达到请求目标时可返回当前状态，完成事件按动作标识去重，不意味着新增事实。
- 同提案并发确认只生成一份新 Profile、一次确认事件。不同旧版本提案竞争时，一个确认成功，另一个明确提示资料已变化，不自动合并事实。相同提案命令标识携带不同事实内容明确冲突，不静默返回另一段旧事实。
- 修复 SQLite 重读时间丢失时区引起的重放响应差异；工作区相关时间统一为协调世界时。
- 保存异常返回结构化 503（可重试、修复动作、关联标识），不暴露 SQL、路径或职业资料。提示“结果尚未确认、先刷新再原操作重试”，不对未知提交结果作虚假的成功或回滚保证。四个网页转发入口保留连接错误为 503；行动/投递/事实表单展示具体修复说明。

## 决策与失败复盘

- 技术决策：事务边界在应用命令外侧，原业务用例不重写；Profile 归一化与版本规则仅有一份。由于本地单库、无外部调用，SQLite 短写事务足够，不引入队列或分布式锁。
- 可复现失败：在合成库为 `application_timeline_events` 加 `BEFORE INSERT` 触发器，仅当 `event_type='evidence_confirmed'` 时中止。应返回 503，Profile/提案/事件全无部分写入；移除触发器后原操作可重试。测试第一次还揭示首次/重放时间格式不同，修复的是实际缺陷而非放宽断言。
- 面试口述：确认一条职业事实会同时改三个地方，分别提交会出现资料已升版而提案仍待确认。我让原用例共用一个 Session，在短事务里检查版本、保存资料、确认提案和事件；异常整批回滚。同提案重试幂等，不同旧提案不会自动合并。测试在最后一步注入失败，验证的不是只有响应码，而是数据库没有半份业务结果。
