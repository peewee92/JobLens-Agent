# 主闭环 5C：限定范围更新分析

> 当前状态（2026-10-27）：5C-1a 预检、5C-1b-1 兼容报告启动、5C-1b-2 有界规则重算与恢复已实现并离线验证。以下需求卡和数字按各轮保留，不代表所有 5C 已完成。新旧结果比较、工作台/工作区入口收敛和完整主闭环验收仍待推进；未授权新收费模型验收。

## 需求卡

- 用户：确认新事实后，希望更新原目标岗位或原批次，而不是无范围重跑全部岗位。
- 当前：只能从 Agent 页另建排序或调用旧单岗位匹配；缺少同一入口的复用/重算/授权预检与保存结果比较。
- 交付拆分：5C-1a 只读预检与结果页入口；5C-1b 同一运行存储中的显式执行/继续和步骤领取；5C-2 新旧结果比较与历史保留；5C-3 工作台/工作区入口收敛及完整浏览器验收。
- 本片完成标准：原结果页可选择目标/原批次，查看真实当前事实版本、可复用报告、每次最多 5 个新增分析候选、需模型或输入修复的岗位；预检不写数据库、不调用模型、不自动启动更新。不把预检称为更新已完成。
- 契约：应用层预检结果 → Python/共享 JSON Schema → TypeScript 页面消费；不保存第二套进度。旧结果与所有未提交工作保留。
- 失败边界：原结果缺失明确错误；岗位或要求缺失给修复入口；当前版本与发布检查变化标记需重新预检。预检是提示，执行时必须重新校验并领取，不能把预检摘要当作授权。
- 不做：本片不调用模型、不写真实数据库、不推送提交，不承诺模型调用次数或匹配改善。OpenSpec 未安装/初始化，采用本卡。

## 已实现（2026-10-26，5C-1a）

- 新增只读 `GET /api/v1/career-agent/runs/{threadId}/update-plan?scope=targets|batch`。目标来自原保存结果；批次来自原运行请求，不扩大到用户全部岗位。
- 当前资料、意向、岗位、提取与最近报告在同一个 SQLite 读快照捕获；沿用既有输入发布检查，并检查检查结果的版本是否仍与快照一致。预检不能替代执行时复验；跨读快照变化标记 `update_inputs_changed`。
- 复用依据是现有报告版本兼容规则。资料/意向/规则/要求/偏好输入变更时不冒充可复用。每次首批最多 5 个需要新增分析的零模型候选，其余留待下一批；模型需求明确展示且不执行。
- 语义模型需求规则由预检、真实语义工作流和旧单岗位重新匹配共用，不再分别维护同一个候选证据判断。不新增业务算法、模型调用或检查点状态。
- 原结果页可进入预检页面，GET 表单切换范围；保持旧结果与事实版本，不在打开页面时重算。

## 技术决策

预检只做现有事实投影，不落一套可与 Agent 运行冲突的“更新进度”。`advisoryOnly=true` 明确说明它不是预留或模型授权。真正执行必须进入既有运行存储，固定本轮版本、按步骤领取与短事务提交；不能因为几秒前预检通过就绕过并发版本检查。

## 可复现失败

`test_missing_database_schema_returns_repairable_503_without_sql_or_private_fact_leaks`：先通过实际流程生成隔离原结果，再仅在测试数据库移除 `match_reports` 表。预检必须返回安全的 503 与副本迁移修复提示，不返回 200 空列表，也不把原始 SQL/驱动错误暴露给网页。此故障仅限临时测试库，未在真实库执行。

`test_one_version_race_blocks_only_that_job_instead_of_reusing_an_unchecked_report` 使用受控发布查询替身模拟检查期间版本变化；证明边界校验有效，不宣称它是实际并发线程压力测试。

### 本轮实现与权衡

- 新运行固定来源运行/结果、范围、输入摘要、职业资料与意向版本、匹配报告标识；这些字段不可在迁移中改写。作为已有运行的类型化字段保存，不新增数据库、不双写更新任务。
- 受理前重新计算预检，摘要变化或任一报告不可复用时拒绝。受理后首次 Continue 再检查；排序遇到不在绑定集的新报告时转为过期。现有恢复前与最终保存检查继续负责当前性校验。
- 复用既有排序与人工确认节点，不自动批准新目标。只有最终保存事务成功才获得新版结果；原结果保持不变。
- 相同标识与内容重放返回原状态，不重新排序或隐式继续；不同内容冲突。受理记录和追加事件沿用同一事务，事件写失败则一起回滚。实际执行使用已有租约。
- 网页发送前持久化请求，丢失响应/刷新后可重放原请求或查看对应运行；只有用户明确核对后才清除本地请求。GET 不执行更新。暂存失败则不发送。
- 接受与事实读取并非一个长事务：接受的是固定版本的命令，不保证此后事实不变。通过继续、排序报告绑定、恢复及结果提交的分层检查阻止变化混入新结果；不承诺外部调用恰好一次。

### 5C-1b-2 实现与技术决策

1. **步骤记录嵌入唯一运行**：当前最多 50 个岗位，使用 `UpdateMatchStep` 与分批命令记录嵌入已有 SQLAlchemy 运行载荷。固定岗位/提取/偏好指纹/原报告标识，不保存简历正文；步骤完成、复用与阻断不能随意改写，命令只能追加。避免额外的更新任务状态机和步骤表同步。以后确需大量跨运行步骤查询时再评估规范化步骤表，当前不新增数据库迁移。
2. **共用业务规则**：原资格用例与预检、固定事实匹配共用 `evaluate_match_eligibility`，包含结构化求职偏好；明确硬冲突时沿用既有 blocked 报告构建，不浪费语义调用。证据检索、语义确定性分支和报告构建均复用现有代码。
3. **零模型能力边界**：规则执行器不持有真实模型客户端，且执行前确认是否需要语义模型；需要时标记等待。`_NoModel` 与禁止模型 Trace 工厂作为第二道防线。没有把报告中的常量调用次数当作独立计量证据；通用模型授权/实际尝试计数仍属后续工作。
4. **短领取、事务外计算、短提交**：每一步实际领取使尝试数增加；报告与步骤完成、运行修订和追加事件在同一事务保存。普通迁移接口不能只伪造“步骤完成”而不保存报告。提交前在 SQLite 写事务中复核固定事实与发布条件，再按租约和修订条件提交；过期执行者即使返回也整体回滚，不能留下晚到报告。
5. **显式有界 Continue**：分批命令含 `actionId/expectedRevision/useCompletedOnly`，每次最多尝试 5 个岗位，失败项不抢占尚未尝试的岗位。相同命令只返回当前原运行；内容不同或新命令使用旧修订均冲突。中断后允许重算纯规则步骤，不承诺计算恰好一次。GET 不执行，模型需求不自动重试。
6. **部分结果由用户明确选择**：默认等待未完成项；用户明确选择后仅用完成/复用岗位进入已有 LangGraph 排序与人工确认。原请求范围保留，未处理岗位在运行和保存结果响应中明确列出，最近记录不显示整批完成。选择部分范围后不能悄悄扩大，后续更新另建独立运行。
7. **失败可查而不过量记录隐私**：单项纯计算失败保存稳定错误码，事件保留实际异常类型；日志只含运行/岗位标识、尝试数与异常类型，不写异常消息、原始职业资料或 JD。数据库提交错误不被当成单项计算失败吞掉。
