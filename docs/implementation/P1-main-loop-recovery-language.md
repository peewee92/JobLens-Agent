# 故障恢复页面的用户可读状态

- 问题：注入结果保存失败后，运行实际可安全继续，但用户页面显示内部标识 `skill_gap_ready` 和英文编排术语，无法直接理解是否已经接受目标、下一步做什么。
- 目标：用当前已保存的步骤显示简短中文说明；未知步骤保守提示查看状态，不暴露内部值、不假称已完成。技术状态和接口不变。
- 边界：不改变状态机、恢复策略、已保存结果和命令；不自动继续、不额外调用模型。
- 验收：中文映射覆盖创建、排序、已确认等待保存及过期等步骤，未知值有安全回退；隔离浏览器重启后实际观察恢复页面，故障前后数据库状态和事件可检查。

## 本轮验证

- 使用独立合成 SQLite，创建单岗位分析后，在完成事件插入处注入故障。浏览器确认目标后得到保存失败提示；SQLite 为 `resuming / skill_gap_ready / revision 4`，没有分析快照，事件 5 条。
- 实际停止后端进程、移除测试故障并重启同一数据库；刷新页面后仍为同一状态、同样 5 条事件，说明查看未推进运行。点击“继续分析”后完成，SQLite 显示 `completed / revision 5`、存在保存结果和 6 条事件；`target_cohort_resume` 只出现一次。浏览器成功打开保存的准备材料。
- 第二个隔离运行重复注入故障并查询状态，页面实际显示“目标岗位已确认，分析结果尚未保存；可以继续分析，不必重复确认。”移除故障后继续成功。
- 全量前端 281 项测试及类型检查通过，包含未知步骤、原型属性名的安全回退测试。`git diff --check` 通过。
- 范围：验证结果保存失败、进程重启和显式继续；没有因此证明所有网络故障或并发场景均通过。仅使用合成数据和离线替身，无收费模型、真实求职数据写入或提交推送。

## 决策与口述

运行状态仍由服务端管理；网页只解释已保存的状态，不为简化文案创造新的状态机。失败例证是用户看到内部 `skill_gap_ready` 却不知道决定是否已接受；新文案明确区分已确认和结果未保存，避免重复确认。
